# EditBook 설계서

작성일: 2026-10-30
상태: 검토 반영 완료, 사용자 승인 대기

## 1. 무엇을 만드는가

교사 10명(집필진)과 출판사 편집장이 교과서·책 원고를 함께 다듬는 **웹 기반 편집실**이다.

원고 자체는 지금처럼 한글(hwp, hwpx) 또는 워드(docx) 파일로 쓴다. 이 프로그램은 그 파일을 올리고, 버전을 쌓고, 편집장이 미리보기 위에 직접 영역을 표시해 수정을 요청하고, 교사가 응답하고, 편집장이 확인하는 **요청 ↔ 응답 ↔ 확인 ↔ 재요청의 고리**를 관리한다.

### 왜 만드는가

지금은 한글·워드 파일을 메신저나 메일로 주고받으며 "이게 최신인가", "내가 고친 걸 편집장이 봤나", "어디를 고치라는 거였지"가 자주 꼬인다. 이 프로그램은 다음 세 가지를 해결한다.

1. **최신 버전이 무엇인지** 언제나 분명하다. 이전 버전도 남는다.
2. **어디를 고치라는 건지** 미리보기 위에 표시가 붙어 있어 말로 설명할 필요가 없다.
3. **지금 누구 차례인지, 몇 개가 남았는지** 책 전체·파트별·요청별로 한눈에 보인다.

### 성공의 모습

- 편집장과 교사가 파일을 메일·카톡으로 주고받지 않게 된다.
- 교사가 로그인하면 "내게 온 요청 N개"가 바로 보이고, 요청을 눌렀을 때 원고의 어느 부분인지 바로 보인다.
- 한 권이 끝나면 책을 보관 상태로 두고, 다음 책을 새로 만들어 같은 방식으로 계속 쓴다.

## 2. 목표 / 비목표 / 반(反)목표

### 목표

- 책 단위 작업 공간. 책마다 참여자, 파트, 원고, 요청이 따로 쌓인다. 여러 책을 동시에 또는 순차로 운영한다.
- 파트마다 담당 교사가 정해져 있다. 담당자와 편집장만 그 파트의 원고를 올리고 요청에 응답한다. 같은 책의 다른 참여자는 읽기만 가능하다.
- hwp, hwpx, docx 파일을 올리면 앱 안에서 바로 펼쳐 볼 수 있다(PDF로 변환한 미리보기).
- 편집장이 미리보기의 특정 페이지·영역을 직접 표시하고 메모를 남긴다. 교사는 그 표시에 답글을 달거나 새 버전을 올린다. 편집장은 확인 완료 또는 재요청으로 응답한다.
- 사진·참고 자료 같은 큰 파일을 파트별 자료함에 막힘 없이 올린다.
- 휴대폰 홈 화면에 설치(PWA)하면 푸시 알림이 온다. 컴퓨터 브라우저에서도 같은 알림을 받는다.
- 클라우드 서버 한 대에서 돌아간다. 설치 프로그램 없이 주소 하나로 접속한다.

### 비목표 (이번에 하지 않음)

- 앱 안에서 원고 본문을 직접 편집하는 기능(구글 문서식 공동 편집). 원고는 외부 프로그램에서 쓴다.
- 이메일·카카오톡 등 외부 메신저 연동. 알림은 웹 푸시와 앱 안 알림만.
- 한글·워드 파일의 문단 단위 자동 비교(diff). 버전 비교는 "두 버전을 나란히 펼쳐 보기" 수준.
- 조판·레이아웃·출판용 최종 파일 생성.
- 앱스토어·플레이스토어 배포.

### 반목표 (이렇게 되면 실패)

- 사진 자료가 용량 때문에 안 올라가거나 올리다 끊긴다.
- 교사가 "어디를 고치라는 거지"를 다시 물어봐야 한다.
- 로그인이나 설치가 복잡해서 교사들이 다시 카톡으로 돌아간다.
- 편집장이 확인했는지 안 했는지 교사가 알 수 없다.

## 3. 사용자와 역할

| 역할 | 누구 | 할 수 있는 것 |
|---|---|---|
| 관리자 | 사이트 운영자(처음에는 의뢰인 본인) | 계정 만들기·비밀번호 초기화, 책 만들기, 책의 편집장 지정 |
| 편집장 | 출판사 편집장 (책마다 1명 이상) | 파트 만들기·담당 교사 지정, 모든 파트에 수정 요청, 확인 완료·재요청, 자기 책의 참여자 초대 |
| 교사(저자) | 집필진 | 자기 파트에 원고 버전·자료 올리기, 자기 파트의 요청에 답글, 같은 책의 다른 파트 읽기 |

- 한 사람이 여러 책에 다른 역할로 참여할 수 있다.
- 로그인은 아이디(이메일 형식 권장)와 비밀번호. 계정은 관리자가 만들고, 첫 로그인 시 비밀번호를 바꾸게 한다. 비밀번호를 잊으면 관리자가 초기화한다. (제 판단: 이메일 연동을 원치 않으셔서 이메일 기반 비밀번호 찾기를 넣지 않음)
- 한 책에 편집장이 여러 명이어도 되지만, 확인 완료는 편집장 역할이면 누구나 누를 수 있다.

## 4. 핵심 개념

```
책(Book)
 └ 참여자(Member: 역할 = 편집장 | 교사)
 └ 파트(Part: 순서, 제목, 담당 교사)
    ├ 원고 버전(Version: v1, v2, … 각각 원본 파일 1개 + 변환된 PDF)
    │   └ 수정 요청(Request: 페이지·영역 좌표, 상태, 대화 스레드)
    │       └ 댓글(Comment: 글 + 첨부 가능)
    └ 자료함(Material: 사진·참고 파일, 용량 큼)
```

### 파트

- 제목, 순서, 담당 교사 1명(교체 가능). 설명 메모(선택).
- 상태는 저절로 계산된다: `원고 없음` / `편집장 검토 중`(열린 요청이 없고 최신 버전을 편집장이 아직 "검토 끝" 표시 안 함) / `요청 N개`(교사 차례) / `확인 대기 N개`(편집장 차례) / `완료`(편집장이 최신 버전에 "이 파트 완료" 표시).

### 원고 버전

- 교사(또는 편집장)가 파일을 올릴 때마다 번호가 하나 올라간다. 덮어쓰기는 없다.
- 각 버전에는 올린 사람, 시각, 한 줄 메모("1·3번 요청 반영")가 붙는다.
- 올리면 서버가 PDF로 변환한다. 변환 중에는 "미리보기 준비 중" 표시, 실패하면 "미리보기 실패, 원본 내려받기"로 안내하고 관리자에게 알림.
- 올리는 사람이 한글·워드에서 직접 뽑은 PDF를 원본과 함께 첨부할 수 있다(선택). 첨부된 PDF가 있으면 서버 변환 대신 그것을 미리보기로 쓴다. 변환이 깨지는 파일에 대한 안전장치다. (제 판단: 미리보기가 없으면 영역 표시가 불가능해 핵심 고리가 끊기므로 반드시 둔다.)
- 이전 버전은 언제든 선택해 볼 수 있고, 두 버전을 나란히 펼쳐 비교할 수 있다.

### 수정 요청

- 편집장이 특정 버전의 특정 페이지 위에 사각형 영역을 그리고 메모를 쓰면 생성된다. 요청마다 파트 안에서 번호(1, 2, 3…)가 붙는다.
- 영역 좌표는 페이지 번호 + 페이지 크기 대비 비율(0~1)로 저장한다. 그래야 화면 크기와 무관하다.
- 상태 흐름:

```
요청됨 ──(교사가 답글 또는 새 버전 올림)──▶ 응답함 ──(편집장 확인)──▶ 확인 완료
   ▲                                              │
   └───────────(편집장이 재요청, 메모 추가)───────────┘
```

- 요청은 만들어진 버전에 붙어 있다. 새 버전이 올라와도 열린 요청은 사라지지 않고 요청 목록에 계속 보이며, "v2에서 표시됨" 배지가 붙는다. 그 요청을 누르면 표시된 버전의 해당 페이지로 이동한다. (제 판단: 다른 파일의 같은 위치를 자동으로 찾는 것은 불가능에 가까워 이 방식을 택함. 편집장이 새 버전에 새 표시를 하고 싶으면 새 요청을 만들거나, 기존 요청에서 "이 버전에 다시 표시"를 눌러 영역을 옮길 수 있다.)
- 교사가 새 버전을 올릴 때 "이 버전으로 응답하는 요청"을 체크박스로 고를 수 있다. 고른 요청은 한꺼번에 `응답함`이 된다.
- 요청 하나에 댓글이 여러 개 달린다. 댓글에는 파일 첨부가 가능하다.
- 교사도 편집장에게 질문을 남길 수 있도록, 담당 교사가 자기 파트의 미리보기 위에 영역을 그려 만드는 "질문"도 같은 구조로 지원한다. 상태는 `질문` → `답변됨`(편집장이 댓글을 달면 자동). 미답변 질문은 파트·책의 "확인 대기 N"에 포함되고, 편집장에게 알림이 간다. 영역 표시 도구는 편집장과 그 파트의 담당 교사에게 열린다. (제 판단)

### 자료함

- 파트마다 하나. 사진, PDF, 압축 파일 등 어떤 형식이든 올린다.
- 파일당 최대 2GB, 올리는 중 진행률 표시, 끊기면 이어 올리기.
- 사진은 썸네일을 만들어 격자로 보여준다. 나머지는 파일명 목록.
- 파일 대신 외부 링크(구글 드라이브 공유 링크 등)만 거는 항목도 넣을 수 있다. 거대한 자료는 드라이브에 두고 링크만 남기는 용도.
- 올린 사람, 시각, 설명 한 줄.

### 알림

받는 사람과 계기:

| 계기 | 받는 사람 |
|---|---|
| 편집장이 요청·재요청을 남김 | 파트 담당 교사 |
| 교사가 답글을 달거나 새 버전을 올림 | 그 책의 편집장(들) |
| 편집장이 확인 완료 | 파트 담당 교사 |
| 댓글이 달림 | 그 요청에 참여한 사람들(작성자 제외) |
| 교사가 질문을 남김 | 그 책의 편집장(들) |
| 파트 담당자로 지정됨 / 책에 초대됨 | 당사자 |
| 변환 실패, 디스크 사용량 80% 초과, 변환 워커 멈춤 | 관리자 |

- 앱 안 알림함(종 모양 아이콘, 안 읽은 개수)과 웹 푸시(설치한 기기)로 간다.
- 푸시를 누르면 해당 요청이 있는 파트 편집실 화면, 해당 페이지로 바로 열린다.
- 사용자는 설정에서 푸시를 끌 수 있다.

## 5. 화면

브레인스토밍 중 보여드리고 승인받은 시안(`.superpowers/brainstorm/…/content/screens.html`) 기준.

1. **로그인**
2. **책 목록**: 참여 중인 책 카드. 카드마다 "내게 온 요청 N", "확인 기다리는 중 N" 배지. 보관된 책은 흐리게 아래에.
3. **책 화면 (파트 목록)**: 파트 한 줄에 제목, 담당, 최신 버전과 날짜, 상태 배지. 내 파트는 눈에 띄게. 편집장에게는 "파트 추가", "참여자 관리" 버튼.
4. **파트 편집실 (핵심)**:
   - 상단 도구줄: 버전 선택, 이전 버전 보기·비교, 영역 표시 모드(편집장), 자료함, 새 버전 올리기.
   - 왼쪽: PDF 미리보기. 페이지 넘김, 확대·축소. 요청 영역이 번호 달린 사각형으로 겹쳐 보임. 열린 요청은 빨강, 완료는 초록.
   - 오른쪽: 요청 카드 목록. 번호, 작성자, 날짜, 상태, 메모, 댓글 스레드, 답글·수정본 올리기 버튼. 카드를 누르면 왼쪽이 그 페이지로 이동하고 사각형이 강조된다. 사각형을 누르면 오른쪽 카드가 강조된다.
   - 휴대폰에서는 위아래로 쌓인다(미리보기 위, 요청 아래). 요청 카드의 "원고에서 보기"로 전환.
5. **자료함**: 파트 안 탭 또는 패널. 올리기 영역(끌어다 놓기), 진행률, 썸네일 격자.
6. **알림함**: 최근 알림 목록, 누르면 해당 위치로 이동.
7. **관리자 화면**: 계정 만들기·초기화, 책 만들기·보관, 편집장 지정, 변환 실패 목록, 운영 상태(디스크 사용량, 변환 대기열, 마지막 백업 시각). (제 판단: 기술 운영자가 따로 없다는 전제로, 관리자가 사이트 안에서 건강 상태를 볼 수 있게 한다.)

디자인 톤: 꾸밈보다 명확함. 글자 크게, 상태 색은 빨강(내 차례)·노랑(상대 차례)·초록(완료)·회색(대기) 네 가지로 통일. 한국어 UI.

## 6. 만드는 방식 (제 판단, 의뢰인이 위임)

의뢰인은 개발 환경을 지정하지 않았고 기술 선택을 맡겼다. 아래는 "10명 규모, 클라우드 서버 한 대, 유지보수 단순"을 기준으로 고른 기본값이다.

- **웹 앱**: Next.js(App Router) + TypeScript 하나로 화면과 API를 같이 만든다. PWA(설치 가능, 서비스 워커, 웹 푸시).
- **데이터베이스**: PostgreSQL. ORM은 Prisma.
- **파일 저장**: 서버 디스크 볼륨에 저장하고 매일 밤 오브젝트 스토리지(S3 호환)로 백업. 저장 경로는 추상화해 두어 나중에 오브젝트 스토리지 직접 저장으로 바꿀 수 있게 한다. 2GB 파일을 위해 조각 업로드·이어 올리기(tus 프로토콜 또는 동등한 방식).
- **한글·워드 → PDF 변환**: 별도 워커 컨테이너에서 LibreOffice headless로 변환. hwp·hwpx는 LibreOffice용 H2Orestart 확장으로 연다. 변환 작업은 DB의 작업 테이블에 쌓고 워커가 순서대로 처리한다(별도 메시지 큐 없음). 변환 품질이 원본과 100% 같지는 않다는 점을 화면에 "미리보기" 표기로 명시한다.
- **PDF 보기·표시**: 브라우저에서 pdf.js로 렌더링하고, 그 위에 요청 영역을 그리는 투명 레이어를 얹는다.
- **알림**: Web Push(VAPID). iOS는 홈 화면에 설치한 PWA에서만 푸시가 되므로 설치 안내 화면을 둔다.
- **인증**: 아이디·비밀번호, 쿠키 세션. 외부 로그인 없음.
- **배포**: 클라우드 VPS 한 대(예: 2 vCPU, 4GB RAM, 100GB+ 디스크). Docker Compose로 앱·DB·변환 워커·리버스 프록시(Caddy, HTTPS 자동)를 띄운다. 도메인 하나 필요. 운영자는 의뢰인 본인이므로 업데이트는 "스크립트 한 번 실행"으로 끝나게 하고, 장애·용량 경고는 관리자 알림으로 보낸다.
- **백업**: DB 매일 덤프 + 파일 볼륨 동기화를 오브젝트 스토리지로.

### 제약

- 한글 파일 변환은 LibreOffice+H2Orestart에 의존한다. 변환이 깨지는 파일이 있으면 원본 내려받기로 대체된다. 초기에 실제 원고 파일 몇 개로 변환 품질을 반드시 확인한다.
- 서버 한 대이므로 동시에 큰 파일 여러 개를 변환하면 느릴 수 있다. 워커는 한 번에 1~2건 처리.
- 푸시 알림은 브라우저가 지원하는 범위 안에서만 된다(안드로이드 크롬, iOS 16.4 이상 설치된 PWA, 데스크톱 크롬·엣지·파이어폭스).

## 7. 만드는 순서 (단계)

각 단계가 끝날 때마다 실제로 쓸 수 있는 상태여야 한다.

1. **뼈대**: 로그인, 관리자 계정·책·파트·참여자 관리, 책 목록·파트 목록 화면.
2. **원고 버전**: 먼저 실제 원고 샘플로 변환 품질 확인. 그 다음 파일 올리기(이어 올리기 포함), 버전 목록, 원본 내려받기, PDF 변환 워커, 사용자 PDF 첨부, pdf.js 미리보기.
3. **수정 요청**: 영역 표시, 요청 카드, 상태 흐름, 댓글, 교사 질문, 새 버전 올릴 때 요청 선택. 파트·책 상태 배지. **여기서 편집장에게 실제로 써보게 하고 피드백을 받은 뒤 다음 단계로 간다.**
4. **알림**: 앱 안 알림함, 웹 푸시, PWA 설치 안내.
5. **자료함**: 큰 파일 올리기, 썸네일, 목록, 외부 링크 항목.
6. **마무리**: 버전 나란히 비교, 휴대폰 화면 다듬기, 백업, 배포 문서.

## 8. 빌더에게 맡기는 것

- 구체적인 DB 스키마, API 경로, 컴포넌트 구조.
- 업로드 라이브러리 선택(tus-js-client+tusd, Uppy 등).
- 썸네일 생성 방식.
- 테스트 전략(단위·통합·E2E).
- 관리자 화면의 세부 배치.
- 상태 배지의 정확한 색상값·아이콘.

## 9. 검토 질문과 답

검토 담당이 올린 질문 중 의뢰인이 답한 것과, 그에 따른 결정.

1. **편집장 동의 여부**: 지금은 프로그램이 아예 없고 카톡으로 주고받는 상태. 편집장이 이 방식을 미리 승인한 것은 아니다. → 3단계(수정 요청)가 끝나는 시점에 편집장에게 실제로 써보게 하고 피드백을 받는 점검을 단계 사이에 둔다. 편집장 환경 제약은 알려진 것이 없으므로 최신 크롬·엣지·사파리를 기준으로 한다.
2. **진행 중인 책 이전**: 없음. 새 책부터 시작한다. 기존 자료 옮기기 기능은 만들지 않는다. 정해진 기한도 없다.
3. **자료 총량**: 모름. 의뢰인은 용량이 커지면 구글 드라이브를 붙이는 것도 생각 중. → 처음에는 서버 디스크에 저장하되 저장 경로를 추상화한다(6절). 자료함에 파일 올리기 외에 **외부 링크 항목**(구글 드라이브 공유 링크 등)을 넣을 수 있게 해서, 거대한 자료는 드라이브에 두고 링크만 거는 길을 열어 둔다. 드라이브 API 연동은 하지 않는다. (제 판단)
4. **원고 샘플**: 추후 테스트. → 2단계 착수 전에 실제 hwp·hwpx·docx 몇 개로 변환 품질을 확인하는 것을 2단계의 첫 작업으로 둔다. 결과가 나쁘면 "사용자 PDF 첨부"를 필수로 바꾸는 것까지 고려한다.
